> 审计时间：2026-11-26　审计方式：源码逐段通读 + 真机实测对照（y430p / TeleAgent 3.1.1 / macOS 13.7.8 x86_64）

## 一、上游 2.0.0 做对了什么

### 1. 密钥机制判断正确（本审计最重要的正向结论）

上游判断「3.x 起 super-agent 的签名密钥由 `ais` 进程持有，不再出现在环境变量或磁盘」，
**在 3.1.1 上完全成立**，实测证据：

| 检查项 | 实测结果 | 证据 |
|---|---|---|
| super-agent(4397) 环境变量 | 只有 `HOME`/`PATH`/`TMPDIR` | `ps eww -p <4367-pid>` |
| ais 环境变量全表（50 项） | 全为 `AIS_*` 系列，无 key 键 | `ps eww -p <ais-pid>` |
| 磁盘扫描 | ais.db（含 wal 副本）+ 全部配置/用户文件，2744 个 43 位 base64url 候选逐个真机验签，**命中 0** | fork 自研探针 `probe_key_from_db.py` |
| 机制解释 | App 生成 key 后经 stdin boot handoff 传给 ais，落进程内存 | ais 二进制字符串 `boot handoff must be one JSON object written to stdin and closed` |

因此「tcpdump 真实样本 + 堆转储验签」是**必要路径**，不是冗余设计。

### 2. 提取器的工程细节值得保留

- lldb 超时自恢复（90s）+ 残留调试器清理 + `kill -CONT` 兜底 —— 防止把 ais 冻死
- 优先无 query 的 `GET` 样本（避免堆内请求缓冲碎片缝合的不可靠样本）
- 多样本交叉验证 + 实机 `GET /plugin` 验证后**才**写盘
- 原子写入 + `0600`；core/pcap 用完即删
- 401/403 自愈（90s 节流 + 文件锁）

这些都被 fork v3.0.0 继承，并补了两处修正（见第三节）。

### 3. 认证协议描述准确

`X-SA-Sign-Version: local-v1` + payload `local-v1\n{METHOD}\n{PATH}\n{TS}\n{NONCE}` +
HMAC-SHA256 + **base64url 无填充**（非 hexdigest）。fork 独立复算签名与真机 200 通过。

## 二、上游 2.0.0 的缺陷（按严重度）

### 高危 H1：`refresh_session_key()` 顺序错误，自愈静默失效

上游 `_try_extract_session_key()` 之前的 `_force_refresh_session_key()` 会先走
`get_session_key()`，而 `get_session_key()` 在环境变量与旧 scheduler 路径都失败后
会**重读 `session.key`**——文件里通常正是刚被判定无效的那个旧值。

实测复现（y430p）：把 `session.key` 写成 43 个 `X` 后重启代理，首个请求 401 →
自愈日志为空 → 请求直接失败。根因是「重读无效文件」把「重新提取」短路了。

**fork v3.0.0 修正**：`refresh_session_key()` 先跑提取器，只在提取器不可用/失败时
才退回重读文件。

### 高危 H2：fork 的 25 项修复完全没有合入上游

逐项 grep 上游 2.0.0（`openai_proxy.py`，3993 行）计数：

| 修复 | 上游计数 | 含义 |
|---|---|---|
| `getincrementaldecoder` | 0 | SSE 逐 chunk 独立 decode → 中文长回复 U+FFFD 乱码 |
| `protocol_version = "HTTP/1.1"` | 0 | 无 keep-alive |
| `MAX_BODY` | 0 | 请求体无上限，慢速连接可占死线程 |
| `client_gone` | 0 | 客户端断开无收尾，日志永久 pending |
| 终态锁存（`_terminal`/`send_error` 锁） | 0 | 可能双 `[DONE]` + 统计双计 |
| `_acquire_session_lock` 会话串行 | 0 | 同会话并发 → 两个客户端收到混合内容 |
| `min_time` 兜底时间过滤 | 0 | 复用会话可能把上一轮回答当本轮 |
| `session_mode` / `config.json` 持久化 | 0 | 默认语义仍是"所有无标题请求共用一个会话" |

也就是说：**上游 2.0.0 = 1.9.10 的代码 + 3.x 密钥层**，1.9.11 之后的所有修复
（含我们 2026-10-19 三路审查的 17 项 + v1.10.1 的 2 中危 6 低危）一概没有。

### 中危 M1：默认仍监听 `0.0.0.0` 且不鉴权

`main()` 默认 `--host 0.0.0.0`，`Authorization` 任意值即放行。局域网内任何设备
都能白用该账户配额。fork v3.0.0 改为默认 `127.0.0.1` + Bearer 常数时间比对。

### 中危 M2：`/api/permission/inject` 注入面

上游保留该接口（虽然限制 localhost），可向 `_pending_confirmations` 注入伪造确认，
进而推送到 QQ/企微通道。fork v3.0.0 直接删除该端点及整条机器人推送链路。

### 中危 M3：`input` 与 `cache.read` 口径混淆

上游把上游 `step-finish.tokens.input` 直接当 OpenAI `prompt_tokens`。真机实测
上游口径是 `total = input + output + cache.read`（`input` 只是未命中缓存部分），
直接映射会**少报** prompt_tokens。fork v3.0.0 改为 `prompt = input + cache.read`。

### 低危 L1：`step-finish` 的 tokens 读取时序

上游在 `session.status=idle` 触发 complete 后不再读事件流；真机实测 `step-finish`
恰好在 `idle` **之前**到达（差 0.00s 级），但一旦上游顺序变化就会丢 usage。
fork v3.0.0 增加终态后排空宽限（`DRAIN_GRACE`），并在终态回调里直接读
`listener.tokens`（而不是等线程 join 后读外部变量）。

### 低危 L2：非流式确认场景语义

上游保留「出现 confirmation 后 2 秒收尾返回」的 fork 修补，但没有自动答复能力；
通用 SDK 收到 `finish_reason=stop` 的空回答会当成模型没说话。fork v3.0.0 改为
自动回 `once`（可配置关闭）。

## 三、fork v3.0.0 相对上游的取舍

**继承**：密钥优先级（env → session.key → 旧路径）、401 自愈、提取器全部安全细节、
OpenAI 端点语义、会话按标题复用。

**未继承（删除）**：
Web 控制台（含 800+ 行内嵌 HTML）、`/api/status|models|logs|sessions|stats|default-model|config|test`、
`/api/permission/inject`、`/v1/embeddings`（转本地 Ollama/vLLM）、
`identify_caller_process` 全套（lsof/ps/万达云穿透）、来源标签与
`build_source_session_title`、`[TOOL_CALL]` 文本协议与 `_build_tool_prompt`、
http(s) 图片代下载。

**删除理由**：
1. 单账号自用不需要舰队级控制台；
2. `build_source_session_title` 是「脚本|PID|日期|时间」这类**人工标题痕迹**的唯一来源，
   删掉后所有会话一律由 super-agent 自动命名，最接近原生使用形态；
3. 把工具定义塞进 prompt 既污染上下文又是反代特征，且上游只有纯文本 prompt 通道，
   客户端工具回路本来就打不通（tarouter 真机已证）；
4. 代下载外部图片属于 SSRF 面，且不是原生行为。

**新增**：
Bearer 鉴权（fail-closed）、默认 127.0.0.1、全局在飞请求上限（默认 2）、
`reasoning` part → OpenAI `reasoning_content` 透传、确认自动答复、
标准库单测 27 项。

## 四、"最小痕迹"能达到什么程度（实事求是）

必须说清楚：**任何本地反代都不可能做到"上游完全无法判断"**。能控制的是这几层：

| 层面 | 本方案的做法 | 残余可观测性 |
|---|---|---|
| 云端流量来源 | 完全不介入——请求始终由官方 `super-agent` Go 二进制发出 | 无（厂商看到的就是官方客户端） |
| 设备/安装指纹 | **不伪造、不改动** `device-meta.json`/`installId`/UA | 无（用的是真实值） |
| 会话命名 | 全部交给 super-agent 自动命名，不写人工标题 | 低（标题风格与人工操作一致） |
| 请求节奏 | 全局并发上限 2 + 同会话串行 | 低（接近单人使用） |
| 协议形态 | 只走 `/session` + `prompt_async` + `/global/event`，与 App 同路径 | 无（同一条协议栈） |
| 代理自身 | 只用 `127.0.0.1` + Bearer，不对外暴露控制台 | 无（不出本机） |

**不承诺的部分**：单账户高频使用本身会造成"用量曲线异常"；这一点无论怎么伪装都
无法消除，只能靠控制节奏与总量。所以本方案的正确用法是**自用级频率**，不是当 API 池对外服务。
